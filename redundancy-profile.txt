READING THE SUMMARY

Calls: number of recorded intervals, not frames. Some stages contain multiple
intervals per function call and some combine Python and native intervals.
Total ms: sum of all runtime intervals.
Avg us/call: Total divided by Calls, converted to microseconds.
No per-thread first-call subtraction is used: the decoder creates fresh field
threads, so such subtraction would remove normal work rather than startup.
Setup n / Setup ms: separate constructor cache preparation measurements.

Python scopes use perf_counter_ns. Compiled functions use QueryPerformanceCounter
on Windows and clock_gettime(CLOCK_MONOTONIC) on Unix, through native LLVM calls.
No Python callback is inserted into compiled loops. Each calling thread has its
own counter buffers. Native ticks are converted to time using the clock frequency.

Native intervals exclude JIT compilation. Enclosing Python intervals can include
compilation, including first calls to different compiled functions after the
first interval in that row. These measurements do not subtract JIT time.

Scopes overlap: 02 can contain 01 and 03, 01 contains 09, 03 contains 12,
04 can contain 05, and 08 overlaps 17. Do not sum all rows. The profile does not
claim to separate the independent speedup attributable to every historical
commit. Thread time can overlap, so accumulated stage time is not wall time.

Zero calls means the path was not executed or has been removed. It does not
mean an operation was measured as taking zero time. Debug-only and optional
paths normally have zero counts unless explicitly enabled by the existing options.

The summary reports raw empty-clock and empty-expression timing floors.
Instrumentation overhead is not subtracted. Context management, counters,
argument passing, and effects on compiled optimization add further overhead.
Very small scalar differences may be below useful profiling resolution. These
branches are for locating costs; their FPS is not uninstrumented benchmark FPS.
